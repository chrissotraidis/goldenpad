### 3.3 Open defects and risks

**F1 — P0 · Confirmed fact (mechanism, in the shipped lineage's source mirror) · magnitude unmeasured in-product — automatic-fire cadence runs at frame rate, not tick rate (TD-01).**
Mechanism, now confirmed in the decomp that mirrors the exact ROM code the static recomp executes (upgraded in revision 2 from the MGB64 oracle alone): the pinned game loop ticks the simulation once per 60 Hz retrace (`workbench_theboy.c:476-641`; the apparent 30-FPS limiter variables are assigned and never read — dead code). GoldenEye advances the player's fire counter *once per rendered frame*, directly beside its tick-scaled twin — `gunfire.c:2698-2702`: `field_890 += g_ClockTimer; field_88C += 1;` — and gates automatics on `field_88C % bondwalkItemGetAutomaticFiringRate(weapon) == 0` (`gunfire.c:3023`, with the burst `volley % 3` path at `:3021`). The guard seam is `chraction.c:6562-6616`: unconditional `firecount[hand]++`, the `% rate` gate at `:6569`, a `% (rate*2)` secondary at `:6573`, and the `-1` line-of-sight retry at `:6616`. Retail advanced these counters at 15–30 Hz (frame cost 2–4); the recomp's locked loop advances them at 60 Hz with `g_ClockTimer == 1`, so the overspeed factor equals the retail frame cost of the scene (~3× typical; MGB64 measured AK-47 33.3 vs 11.3 shots/100 ticks). GoldenEye64Recomp's README admits the defect; its patch tree contains no repair; GoldenPad's patch adds no timing hunks; "Original refresh" is presentation-only (`recomp_game_start.cpp:199-204`).
**Why tests miss it:** no GoldenPad measurement exists at all — the ledger says so. **Smallest step:** a read-only RDRAM probe using the existing `monitorGameState` polling pattern — sample the tick counter plus the current-magazine word at ~10 Hz and derive shots-per-tick from the ammo-delta slope; a single 30-round magazine spans the 100-tick gate window at either cadence, so no inventory injection is needed. Guards need one diagnostics-only log line at the fire seam (MGB64's trace flag is the template). **Narrowest repair (exact seams named):** `RECOMP_PATCH` only the two fire functions (never `bossMainloop`): scale the divisor at the player gate (`gunfire.c:3023` pattern) and the guard gates (`chraction.c:6569/6573` pattern); preserve the semi-auto `rate <= 0` pass-through, the burst `volley % 3` logic, and the guard `-1` retry pairing (`:6616`). **Rollback:** independent patch. **Acceptance:** before/after shots-per-100-ticks matching the source-derived expectation, player and guard together, then hands-on combat re-acceptance.

**F2 — P0 · Confirmed — modern sidestep unimplemented (TD-02, issue #8).**
Touch MOVE maps straight onto the N64 stick (turn); controller Modern maps both horizontal axes to turn; only "Original N64 C-buttons" strafes, emitting C-left/right from right-stick X at a 0.30 post-curve threshold with no hysteresis (`RecompPrototypeInput.swift:326-390, 526`). The touch template has no C controls at all (`RecompPrototypeTouchLayout.swift:42-70`). Commit `b436ece` is docs-only. Repair constraints established by this review: the remap must be game-side (see R2 — the host cannot classify state), behind a **new** stored mode value (the ledger's rule against silently changing saved preferences), with the pure mapping test `TESTING.md:137-138` already requires, and it must account for GoldenEye's in-game control styles (1.2 "Solitaire" already swaps stick/C semantics — a remap assuming 1.1 composes wrongly; the issue thread shows this is live). Fold R1 and C-threshold hysteresis into the same acceptance pass, since sidestep-gate items 4–5 already demand them.

**F3 — P0 · Confirmed report · cause Unknown · code-path divergence Strong inference — A12X first-frame crash (TD-03, issue #9).**
Deterministic SIGSEGV at `KERN_INVALID_ADDRESS 0x520` in the A12 driver's `drawIndexedPrimitives`, via `plume::MetalCommandList::drawIndexedInstanced` ← `RT64::FramebufferRenderer::submitRasterScene`, on the verified Preview 1 IPA `a3aa3700…`. The A12X sits *inside* the declared envelope: arm64 + metal capabilities, iOS 17 target, device families 1,2 — **no `MTLGPUFamily` or GPU-generation floor exists anywhere in CMake/Config/patches** (grep-confirmed). Evidence lane: full redacted `.ips` with binary UUIDs/load addresses (offered by the reporter, not yet attached), a Preview 2 reproduction on A12-family hardware, and a matched newer-device control — before any renderer repair or support-floor change.
**New in revision 2 — a concrete, family-gated code-path divergence that only A12-class hardware executes.** Plume selects its descriptor-binding strategy per device: `useArgumentBuffersTier2 = argumentBuffersSupport() == Tier2` and `useDirectBufferAddresses = Tier2 && supportsFamily(GPUFamilyMetal3)` (`plume_metal.cpp:3845-3846`). Every device in the project's acceptance history (iPhone 14 / A15, iPad Pro M4) is Metal3-family; the A12X is not (Metal 3 requires A13+/M1+ per Apple's published support list), so on the A12X `useDirectBufferAddresses` is false — a binding configuration *no accepted device has ever run*. Worse, the configuration is mixed: with Tier 2 but no Metal3, textures and samplers are written into the argument buffer as raw `gpuResourceID()` values while buffers go through the `MTLArgumentEncoder` into the same argument buffer (`plume_metal.cpp:1824-1860`, encoder attached at `:1700-1701`); direct ResourceID writes are a Metal 3 idiom, and mixing them with encoder writes is only guaranteed coherent on Metal3 hardware. A garbage-bound texture or sampler reaching the first draw would produce exactly the observed driver-side dereference at a fixed offset inside `drawIndexedPrimitives`. (Plume deliberately binds a `nullBuffer` for unbound vertex streams — `:3848` — which points away from a simple nil-buffer and toward the descriptor path.) This is a *Strong inference about the divergence, Unknown for causation* — the fault could still be driver-internal — and it does not authorize a fix. But it sharpens the evidence lane with an experiment that needs **no A12 hardware**: build a diagnostic candidate with `useDirectBufferAddresses` forced false (one boolean; and a second variant forcing the Tier-1 encoder path) and first-frame-test it on the accepted iPhone/iPad. A reproduction localizes the defect to Plume's non-Metal3 binding path and lets a repair be developed on available hardware before A12 confirmation; a pass narrows the remaining space to Tier-1 semantics or the driver itself. It also tells the `.ips` reviewer exactly what to look for: which resource type the faulting draw dereferenced.

**F4 — P1 · Confirmed — lifecycle freezes are unobservable with the current counters (TD-04).**
The three counters mark *entries*: dl at `send_dl` entry, vi at `update_screen` entry, presented after `updateScreen` returns — present-*enqueued*, not on-glass, and skipped while inactive. The Gfx thread can block inside those calls after the counter ticks: busy-spin ring waits (`rt64_workload_queue.cpp:50-58`, `rt64_present_queue.cpp:38-46`), a game-side Metal fence wait in the CPU-framebuffer upload path (`rt64_state.cpp:1915-1924`), and — most dangerous — Plume's `waitForCommandFence` at `dispatch_semaphore_wait(…, DISPATCH_TIME_FOREVER)` (`plume_metal.cpp:3731-3734`), reached from the per-frame present submit. The frozen signature `vi == presented+1` is produced identically by fence wait, ring backpressure, or the nil-drawable resize loop — "presentation-stalled" does not uniquely identify drawable failure, and "no-runtime-progress" describes the counters, not a fault. Session separation is partial: the crash marker is removed on *every* backgrounding, so a frozen-then-force-quit session records as a clean end (`recomp_game_start.cpp:713-717`) — the exact case TD-04 is about. Smallest correction: a bounded fence wait (log-on-timeout, generous bound) plus phase brackets at the six named wait points; keep screenshot / Control Center / lock / app-switch / background as separate physical cases (the code already treats `.inactive` and `.background` differently on iOS and identically on Mac).

**F5 — P1 · cause Unknown (mechanisms bounded) — audio static; the one free discriminator was never captured (TD-05).**
Pipeline at this HEAD: requested rate logged and ignored (`recomp_game_start.cpp:426-428`); Swift builds a 22,050 Hz source node with engine-side conversion (`RecompPrototypeAudio.swift:82-106`); ring 65,536 frames (~2.97 s); 1,024-frame reserve; overflow discards with a counter; underrun does a 32-frame fade + re-prime. **Rate mismatch is ruled out at source (revision 2):** GoldenEye requests exactly `OUTPUT_RATE 0x5622` = 22,050 Hz (`audi.c:19,340` in the decomp mirroring the shipped ROM), and librecomp deliberately skips console DAC quantization and returns the request verbatim (`librecomp/src/ai.cpp:9-16`) — producer, runtime, and host all agree at 22,050 Hz (retail hardware would have played ≈22,048 Hz; a 0.009 % authenticity nuance, not an artifact source). The hypothesis space narrows to: mid-stream overflow-discard discontinuity, the lifecycle ring-reset race, cadence/underrun jitter, and post-engine route artifacts. The race is confirmed structurally: the route-change observer calls `activate()` unconditionally (`:39-45`), so a route change while backgrounded can leave the render thread live when the foreground ring reset (`audioReadFrame.exchange`, main thread, `:700-709`) fires — up to ~3 s of stale audio can replay with *zero counters incremented*. No `mediaServicesWereReset` handling. Smallest sufficient evidence before touching reserve/latency: one physical session that audibly reproduces static while capturing (a) the requested-Hz log line — predicted value 22,050, doubling as a deployed-binary consistency check — and (b) the 2 s counter series, time-correlated against an externally recorded audio timestamp. Counters moving → cadence class; flat → the counter-invisible classes, justifying the sine/ramp gate next. (The claim that reserve was tuned from Simulator underruns is unfounded — the only Simulator figure is explicitly disclaimed.)

**F6 — P1 · Strong inference, unmeasured — residual flicker's leading hypothesis is entailed by source (TD-06).**
Post-repair, the two depth framebuffer keys (unshifted, and shifted by one screen) still have overlapping byte ranges; every pass's `changeRAM` marks the sibling `rdramChanged` (`rt64_framebuffer_manager.cpp:905-916`) → depth `formatChanged` (`rt64_state.cpp:564`) → discard/clear/rebuild-from-RAM (`rt64_workload_queue.cpp:757-780`). Per-frame mutual churn in multiplayer is *predicted* by source analysis. Confirmed context: GoldenEye reshuffles player render order every frame (`player.c:626-641`, three `randomGetNext()` swaps, called from `boss.c:521`) and gates global work to the shuffle-first player (`bg.c:1056`, `bondview2.c:10237-10245`). Gate refinements this review adds: the counter must sit at the `imgFormatChanged` branch **and also count non-formatChanged depth uploads** (readHeight-growth re-reads, `:779-790`); calibrate against a throwaway pre-repair build to guard a false zero (a genuine zero would contradict the source prediction and suggest a misplaced counter); a fixed-order diagnostic must preserve the three `randomGetNext()` calls or it changes the RNG stream and confounds itself — and even a flicker-free fixed-order run only proves order-dependence, never which mechanism. A zero-churn observation would rule out aliased-depth churn; it would *not* rule out color-image rebuilds, non-formatChanged uploads, authentic lighting dynamics, or host-side temporal effects. Acceptance requires continuous video with frame-local counter alignment; a clean still proves nothing.

**F7 — P1 · Confirmed — no automated build proof of the shipped binary; private pins.**
The only build verifier (`verify-recomp-prototype-host.sh`) compiles the ROM-free *stub* host, not the game-bearing app; the game build is manual and requires the private runtime revision plus private ROM-derived AOT sources (`CMakeLists.txt:77-91, 277-288`); no tracked build script exists for the iOS runtime archives. The package verifiers are strong *content* audits (shape, plist, unsigned, contamination names/magic/two hashes, symbol presence, license notices, deterministic digest) — they prove nothing about provenance, install, launch, conversion, or play. The docs' own proof-chain language is honest about this; the gap is structural, not rhetorical.

**F8 — P2 · Confirmed — Mac mouse ceiling arithmetic; no loss accounting (TD-08).**
Three clamp stages: Swift 60 Hz publish — `scale = 1,680 × sensitivity`, `Int32` clamp ±32,767, excess silently zeroed (`RecompMacInput.swift:496-506`; at default sensitivity any frame delta ≥ ~7.8 px saturates); C-side CAS accumulator clamped ±32,767 (`recomp_game_start.cpp:167-173`); consumer normalization to [-1, 1] sharing one budget with the right stick (`:825-832`); game-side 3°/1° per frame → 180°/s hip, 60°/s aim. No saturation counter exists at any stage; sensitivity cannot fix a ceiling. Safe repair shape: keep absolute controller paths normalized exactly as-is; widen only the *relative* queue budget behind `GOLDENPAD_RECOMP_MAC` (queue bound, consumer pass-through for the queued component, matching Swift pre-clamp), add saturation counters, and measure live loss first — no player/camera memory writes. (Touch look on iOS shares the same structural ceiling, undocumented — P3.)

**F9 — P2 · Strong inference (doubly corroborated) — the Mac "WASD didn't move" report, ranked from this code.**
The reported endpoint — `menu=11 stage=33` with an early stage timer — decodes to `MENU_RUN_STAGE` on Dam immediately after load, now doubly corroborated: `MENU_RUN_STAGE` is ordinal 11 in the decomp's own enum (`bondconstants.h:1832-1843`), and the project's in-repo probe record states the gameplay probe "waits for Dam's frozen intro camera to release, then drives the normal … path" (`STATUS.md:309-310`) — the project has already documented that Dam begins in a non-interactive camera state during which input does not move the player. During that window the host gate correctly reports gameplay-active, W/S is published as stick ±80 and *accepted* by `getInput`, and the game simply doesn't apply it yet. That is the top-ranked explanation. The documented newer-build patch-pair regression (regenerating `patches.c` without the modern-controls patch) explains dead *mouse/crouch* but **not WASD** — W/S flows through librecomp's stick path and is patch-independent. First-responder loss is a real secondary candidate: focus is asserted once at attach and on click, never re-asserted on key-window changes, and mouse capture engages without a click (`RecompMacMetalCanvas.swift:229-256`, `RecompMacInput.swift:441-446`). Saved bindings fall back safely on invalid values. **Single discriminator using only existing logs:** during the symptom, tap E/Space/A/D and export diagnostics — `controller 1 buttons` transition lines prove AppKit delivery and host publication (⇒ game-side/intro); their absence proves host-side loss. Stick values have no log marker at this HEAD; add a zero↔nonzero transition line and a gameplay-active flip line.

**F10 — P2 · Confirmed — controller model gaps beyond the leak; one upstream bug.**
No stable identity (enumeration order decides Player 1); port 1 is touch-only and only in two-player test mode; ports 2–3 are render-only neutral (zeros hardwired). The three multiplayer statuses — rendering (experimental, works), controls (P1 + test-mode P2 only), network (absent) — are genuinely independent, and code and docs agree. **Upstream bug found in the vendored runtime:** `__osContGetInitData` writes `*pattern = 1 << controller` — assignment, not OR (`ultramodern/src/input.cpp:74`) — so the connected-port bitpattern is wrong whenever more than one port is attached; impact on GoldenEye is Unknown (its joy layer likely reads per-port `err_no`, which is filled correctly), but any bitpattern consumer is affected. Minimum production slot model: persistent identity; a host-owned four-slot table + connected bitmask published atomically with port state; first-free assignment with a reclaim-window vacancy; an explicit touch slot that never moves on device events; neutral-until-release on every ownership change; foreground re-enumeration; a separate Mac policy.

**F11 — P2 · Confirmed (chain) / Strong inference (backup exposure) — privacy and hygiene gaps.**
(a) librecomp writes a *second full ROM copy* — the chain is confirmed end-to-end: the host registers `Application Support/GoldenPadRecomp` as the recomp config path (`RecompPrototypeMetalCanvas.swift:92-93` → `recomp_game_start.cpp:489-490`), `select_rom` runs on every start (`:508`), and validation success executes `write_file(config_path / "<game_id>.z64", rom_data)` (`librecomp/src/recomp.cpp:387-388`). The directory is created with plain `createDirectory` — no `isExcludedFromBackup`, no protection attribute — and Application Support is backed up by default, so the user's ROM bytes likely enter device/iCloud backups, contradicting the documented intent for the carefully protected Documents copy. (STATUS's "derived cache is excluded from backup" line belongs to the Legacy host — `PlatformServices.swift:192` — not this path.) On-device only; not a distribution leak. (b) The iOS target lacks `-ffile-prefix-map` (Mac has it, `CMakeLists.txt:184-191`); the six `/private/tmp` literals are held in place by a verifier allowlist rather than toolchain hygiene. (c) Path scans miss `/var/folders`; `check-no-rom-data.sh` is exact-size/hash only and its BSD `stat -f` fails closed on Linux.

**F12 — P3 · Confirmed — input-feel details.**
Classic C-threshold 0.30 applied after dead zone + 1.5 response curve (effective raw ≈ 0.45), no hysteresis — boundary jitter re-triggers C bits at 60 Hz; the legacy host uses 0.42 pre-curve, so the two hosts' "Original C-buttons" feel different and no test pins either number. Aim scale/inversion can disagree between the host half (keyed on the published R bit) and the game half (keyed on `insightaimmode`) when R is remapped. The primary host has no settings schema/migration mechanism (only a `.v1` key suffix), unlike the legacy schema-7 store — relevant to how the #8 fix stores its new mode.

**F13 — P3 · Confirmed — sky/water correctly classified; the "disabled skyRender" nuance resolved (TD-10).**
Both things are true: RT64 does not implement GoldenEye's custom-microcode sky/water RDP commands (upstream omission, admitted in the pinned README), *and* the pinned `skyRenderTri`/`skyRenderFull` patches are fog-fill approximations that ignore every texture/vertex argument — GoldenPad inherits them and only viewport-scopes the fills. The live original `skyRender` still executes its `IsWater`/`WaterImageId` branch (`sky.c:829-883`), performs texture selection, then degrades to the patched fill — flat Frigate water is that path. The full textured-sky reimplementation is `#if 0` dead code; do not enable it wholesale. Glass/monitors/framebuffer feedback, missing geometry, and multiplayer LOD reductions remain separate, unreduced classes needing per-stage reproducers (stage, room, position/yaw/pitch, settings, mode, full-frame capture, matched reference), exactly as the ledger requires.

**F14 — P3 · Strong inference (owner) / Observed (strip) — Mac thin right edge (TD-09).**
Mobile masks the same seam family with a one-point trailing overlay (`RecompPrototypeApp.swift:78-85`); the Mac ZStack has no analog, and **no tracked patch substitutes drawable size for the window contract** (verified across all patches — the rejected experiment is genuinely absent from the tree). One caveat keeps ownership below Confirmed: the Mac strip is *blue* over an all-black host clear, so its color likely originates inside RT64's presented drawable rather than the host ground — a mask still covers it either way. Gate: measure the strip at several window sizes, then fixed-camera Dam/Surface before/after captures where *only* the strip region changes.

**F15 — P3 · Confirmed — screenshot (`.inactive`) neutralizes P2 touch while the game runs.**
Deliberate trade-off to avoid stranding drawable acquisition; in a two-player match a screenshot transiently drops P2's input. Note-only; consistent with the accepted design.

## 5. Cross-issue causal map

- **The generated patch-pair contract is the single most fragile seam.** The documented Mac incident — `patches.c`/`patches_bin.c` regenerated without the modern-controls patch, leaving host producers with no game-side consumers — is the proven failure mode. The CMake string guard now trips on missing bridge calls, but proves linkage, not semantics. The #8 fix, the watch gate, Mac mouse/crouch, unlock, and return-to-title all live on this one seam; regenerate both halves together, always.
- **Main-thread responsiveness is one seam with three distinct failure owners.** Both input publishers are main-thread timers; Plume's per-present main-queue dispatch starved input once on Mac (now bounded by the coalescing patch — load-bearing); sheets and scroll tracking stall the iOS timer in default run-loop mode. "Rendering fine, input dead" therefore has at least three causes on the same thread — which is why the Mac WASD candidates must be discriminated by logs, not assumed.
- **Game/VI scheduling is the shared substrate of three different problems.** The wall-clock VI thread plus the retrace-tick loop simultaneously produces the fire-rate defect (per-frame counters at 60 Hz), blocks netplay (no reproducible frame identity, droppable VI messages, wall-clock `osGetCount`), and makes "no-runtime-progress" ambiguous (the game thread parks when dp/vi messages stop arriving from a blocked Gfx thread).
- **The RT64 present queue and Plume fences are one locus for three symptoms.** Lifecycle stalls (busy-spins + the unbounded fence), the A12X crash (inside `submitRasterScene`'s draw submission, with the descriptor-binding divergence of F3), and the flicker instrumentation (counters must live in the workload/present queues, not the game patch) all converge here — one diagnostic RT64 build can serve TD-04 and TD-06 without touching the frozen depth repair.
- **Controller publication is level-held atomics with no heartbeat.** That single design choice produces the disconnect leak, stale-held-state on resume, and the late crouch edge — and the same `getInput` callback is the future netplay input-injection seam. Fixing ownership fixes the netplay seam's semantics for free.
- **One scenePhase handler crosses four debt items.** Touch neutralization, the audio ring reset (and its race), diagnostics marker hygiene (the false-clean), and presentation suppression all hang off the same few lines — changes here must land one at a time against a fresh baseline, exactly as the ledger's change-control rules demand.
- **Audio cadence couples to lifecycle, not to the renderer.** The per-VI producer and the engine's variable pulls interact with the ring reset and route handling; nothing couples audio to RT64 state — keep those evidence lanes separate.
